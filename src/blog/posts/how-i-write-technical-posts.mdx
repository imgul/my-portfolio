<TLDR>

Write for one reader with one problem. Lead with the answer, then the reasoning, then the details. Edit for the skimmer first: headings, summaries and visuals should tell the story on their own.

</TLDR>

I was the technical editor of my university’s magazine, and I’ve written a lot of documentation since. The posts that work best all follow the same process. This post explains it, and it doubles as the reference for every component this blog supports, so you can see each one in context.

## 1. Find the one idea

Before writing, finish this sentence: *“After reading this, the reader will be able to …”*. If you need two sentences, you have two posts.

It also helps to know which kind of document you’re writing. The Diátaxis framework <Cite id="diataxis" /> splits technical writing into four kinds:

| Type | Reader’s question | Example on this blog |
| --- | --- | --- |
| Tutorial | “Teach me.” | A first Laravel API |
| How-to guide | “Help me do this task.” | [Multi-tenant Laravel](/blog/multi-tenant-laravel-saas) |
| Explanation | “Help me understand.” | [RAG for exam generation](/blog/rag-for-exam-generation) |
| Reference | “Give me the facts.” | This component list |

## 2. Lead with the answer

Readers decide in seconds whether to keep reading. Put the conclusion first, in a summary box:

</TLDR>

## 3. Structure for skimmers

Most people skim first and read second. Good headings, short paragraphs and lists let them find what they need. Every heading on this blog gets an anchor link (hover it and click the `#`), and the table of contents follows you as you read.

### Callouts

Use callouts sparingly, for things the reader must not miss.

<Callout type="note">A `note` adds useful context.</Callout>

<Callout type="tip">A `tip` is a shortcut or best practice.</Callout>

<Callout type="warning">A `warning` flags something that can go wrong.</Callout>

<Callout type="danger">A `danger` callout is for data loss, security or money.</Callout>

<Callout type="insight">An `insight` is the non-obvious idea in the post.</Callout>

<Callout type="success" title="Custom titles work too">A `success` callout reports a result.</Callout>

## 5. Help the reader decide

Founders and engineers read to make decisions. Make the trade-offs explicit.

<ProsCons title="ProsCons" pros={["Makes trade-offs scannable", "Forces you to be honest about downsides"]} cons={["Oversimplifies nuanced choices"]} />

<Decision title="A Decision record (ADR)" status="Proposed" date="Nov 2026">

**Context.** Why a decision was needed.

**Decision.** What we chose.

**Consequences.** What gets easier and what gets harder.

</Decision>

## 6. Write like a person

Plain words beat clever ones. Zinsser’s advice still holds: strip every sentence to its cleanest components <Cite id="zinsser" />. Use “I” and “you”. Explain jargon the first time, like <Term def="A score that measures how well retrieved results match what you needed.">retrieval quality</Term>, with a `Term` that shows a definition on hover or tap.

Side comments that would interrupt the flow go in a sidenote.<Sidenote>On wide screens this sits in the margin. On phones, tap the mark to open it inline.</Sidenote> Classic footnotes work too.[^1]

## 7. Edit, then edit for the skimmer

- [x] Read only the headings. Do they tell the story?
- [x] Read only the summary and takeaways. Is the answer there?
- [x] Cut the first paragraph. Was it throat-clearing?
- [ ] Read it aloud. Fix every sentence you stumble on.

<Takeaways>

- One reader, one problem, one idea per post.
- Lead with the answer.
- Structure for skimmers, then write for readers.
- Make trade-offs explicit and cite your sources.

</Takeaways>

<Update date="22 Nov 2026">

Use an `Update` block when you change a published post, so returning readers know what’s new.

</Update>
