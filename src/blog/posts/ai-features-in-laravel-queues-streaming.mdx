<TLDR>

Treat an LLM like a slow, unreliable third-party API, because that’s what it is. Stream when a user is waiting, queue when they aren’t, and always add timeouts, retries, caching and cost logging.

</TLDR>

The first AI feature I shipped in a client app called the OpenAI API directly inside a controller. It worked in the demo. In production, requests took 10–30 seconds, PHP-FPM workers piled up, and one slow upstream response made the whole app feel broken.

Here’s the pattern I use now.

## Two kinds of AI work

    { label: "User waiting?", note: "chat, autocomplete" },

**Interactive** work, like a chat reply, should *stream* so the first words appear in under a second. **Background** work, like generating 40 exam papers, belongs in a queue.

## Streaming with server-sent events

```php title="app/Http/Controllers/AssistantController.php" {6,12}
public function stream(Request $request, LlmClient $llm)
{
    $prompt = $request->validate(['q' => 'required|string|max:2000'])['q'];

    return response()->stream(function () use ($llm, $prompt) {
        foreach ($llm->stream($prompt) as $chunk) {
            echo 'data: ' . json_encode(['t' => $chunk]) . "\n\n";
            ob_flush();
            flush();
        }
        echo "data: [DONE]\n\n";
    }, 200, [
        'Content-Type' => 'text/event-stream',
        'Cache-Control' => 'no-cache',
        'X-Accel-Buffering' => 'no', // stop Nginx buffering the stream
    ]);
}
```

<Callout type="warning" title="Nginx will buffer your stream">

Without `X-Accel-Buffering: no` (or `proxy_buffering off`), Nginx collects the whole response before sending it, and streaming silently stops working.

</Callout>

On the frontend, read it with `EventSource` or a `fetch` reader and append tokens as they arrive.

## Queued generation

```php title="app/Jobs/GenerateExamPaper.php"
class GenerateExamPaper implements ShouldQueue
{
    public int $tries = 3;
    public int $timeout = 120;

    public function backoff(): array { return [5, 30, 120]; }

    public function handle(LlmClient $llm): void
    {
        $paper = $llm->json($this->prompt(), schema: ExamPaper::schema());
        $this->exam->update(['content' => $paper, 'status' => 'ready']);
        broadcast(new ExamReady($this->exam));
    }
}
```

Use a dedicated queue (`->onQueue('ai')`) with its own workers, so slow AI jobs never block password-reset emails.

## The boring parts that matter

<Tabs>
<Tab label="Timeouts">

Always set a client timeout. A hung upstream connection should fail fast, then retry, rather than hold a worker forever.

```php
Http::timeout(60)->connectTimeout(5)->retry(2, 500)->post($url, $payload);
```

</Tab>
<Tab label="Caching">

Identical prompts deserve identical answers. Hash the model, prompt and parameters and cache the result.

```php
$key = 'llm:' . hash('xxh128', $model . $prompt . json_encode($params));
return Cache::remember($key, now()->addDay(), fn () => $this->call($prompt));
```

</Tab>
<Tab label="Cost logging">

Log tokens per tenant and per feature. Without this you can’t price the product.

```php
LlmUsage::create([
    'tenant_id' => $tenantId,
    'feature'   => 'exam_generation',
    'model'     => $res['model'],
    'input'     => $res['usage']['prompt_tokens'],
    'output'    => $res['usage']['completion_tokens'],
]);
```

</Tab>
</Tabs>

## A checklist before shipping

- [x] Streaming for anything a user waits on
- [x] Dedicated queue and workers for background AI jobs
- [x] Timeouts, retries with backoff, and a clear failure state in the UI
- [x] Cache for repeated prompts
- [x] Per-tenant token and cost logging
- [ ] Rate limits per user, so one person can’t burn the monthly budget

<Takeaways>

- An LLM is a slow, flaky third-party API. Engineer it like one.
- Stream when someone is watching; queue when nobody is.
- Separate AI workers from the rest of your queue.
- Log cost from day one, or you won’t know if the feature is profitable.

</Takeaways>
